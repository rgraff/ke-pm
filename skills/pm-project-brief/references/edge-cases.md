# Edge cases — /pm-project-brief

## The user hands you a PRD or a big spec

Mine it, do not convert it. Pull out what answers the six sections; leave the
requirements, acceptance criteria, and sequencing behind. Tell the user where
that material goes: onto the tasks, as the work pulls for it.

A Brief that is a compressed PRD is still a PRD. It carries the same problem —
detail fixed before anyone learned enough to fix it.

## It is really an initiative, not a KE project

Signs: no describable end state, spans quarters, covers several separate efforts,
and the only name that fits is open-ended ("Improve onboarding").

Say so, then find the bounded KE project inside it — the first piece with an
agreed conclusion. Write the Brief for that, and leave the rest as pieces to
start later.

`ke-pm` does not record initiatives yet, so there is nothing to file the
umbrella against. Name it in the conversation and move on.

## The name breaks the rules

Say which rule, in one sentence, offer two or three alternatives, and let the
user decide. If they keep it, record it and move on. Their call.

Worth doing even mid-Brief: the name is cheap to change until the List has been
in reports and Slack posts.

## The Brief already exists and is badly out of date

Do not rewrite it wholesale in one pass. Read it, show the user what you think
has changed, and work section by section. A Brief is a shared document, and
replacing it silently destroys someone else's edits along with the stale parts.

## The KE project is nearly finished

Write it anyway if it is missing, but keep it honest — describe the problem as
it was understood, not as it is now that everyone knows the answer. A
retroactively confident Brief is worse than no Brief: it teaches the wrong
lesson about how much anyone knew at the start.

## Everything is TBD

If `Approach` and `Open Questions & Risks` are TBD, that is normal at kickoff —
publish it.

If `Problem`, `Goals`, or `Users` are also empty after a real interview, the KE
project is not ready to open. Say that plainly, publish what exists, and put the
gap in `Open Questions & Risks` where it will be seen.

## The Brief is a proposal, not a greenlit KE project

Perfectly normal, and the most common reason a Brief lives outside ClickUp. A
Brief is often written to argue for the work — to get buy-in before anyone
commits to it. There is no KE project yet, so there is nothing to put a List on.

Write it exactly the same way. The six sections are what makes the case: a clear
problem, a measurable goal, and an honest list of what is unresolved is more
persuasive than a pitch. Then hand the user the markdown and suggest keeping it
in the Claude Project until there is a decision.

Do not push them toward ClickUp, and do not treat the missing List as a problem
to solve. When the work is greenlit, `/pm-project-init` sets the List up and
takes most of what it needs from the Brief that already exists.

## A live KE project's Brief is being kept somewhere private

Different situation. Once the KE project is real and has a List, its Brief
belongs on that List where the squad can find it — context on the work rather
than scattered across tools and DMs. A Brief that only the owner can read stops
doing the job it exists for.

If the content is genuinely sensitive, that is a ClickUp permissions question,
not a reason to keep it in a different tool.

## Multiple KE projects in one conversation

One Brief at a time, each on its own List. If the interview reveals two distinct
problems with two distinct end states, say so — that is usually two KE projects,
and noticing it early is worth more than the Brief you were about to write.
